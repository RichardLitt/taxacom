position to be working on collections without direct and immediate
supervision as this particular team apparently did.

one.

original posting.

>> Hi David,
>>
>> Your critical comment below relates to two separate issues:
>> 1. The lack of convenient feedback tools for reporting identification
>> errors in online data portals for DNA barcoding information;
>> 2. The poor quality of data submitted to such portals.
>>
>> With regards to #2, I can only say that the data are as good as we
>> (collectively) make them. E.g., many providers of specimen provenance
>> information do not indicate (and often do not know) the name of the
>> identifier at the time of submission.
>>
>> With regards to #1, I must note that such tools are available. For
>> example, the Barcode of Life Data System has an attribution section for
>> each specimen record that denotes the name of the identifier (when
>> available) and the name of the project manager who could be asked to
>> address taxonomic problems within a particular dataset. E.g., see public
>> BOLD record below (bottom right corner):
>>
>> http://v3.boldsystems.org/index.php/Public_RecordView?processid«SMS268-06
>>
>> Because of privacy/spam concerns, it is not possible to email the
>> identifier or project manager directly from a public specimen record - this
>> functionality is only open to registered BOLD users who are logged in.
>> However, if users wish to provide instant feedback, they have the option
>> to annotate the data record by clicking the Add Tags&Comments button just
>> above the taxonomy - this will flag the record for future users.
>> They can also add tags on the corresponding BIN page which would annotate
>> all specimens putatively referred to a given species:
>>
>> http://v3.boldsystems.org/index.php/Public_BarcodeCluster?clusteruri=BOLD:ACF2193
>>
>> I am not sure if I fully understand your remarks about 'proper' or
>> 'correct' identifiers. If you imply that some barcode data records are
>> contributed by people without adequate taxonomic expertise or
>> accreditation, I personally think that it is a strength of such large-scale
>> data projects.
>> In most other real world situations, the 'proper' and 'correct'
>> identifiers are those who get acknowledged in specialized taxonomic
>> revisions, whereas many of the the 'incorrect' and 'improper' ones write
>> volumes of ecological assessment and biodiversity survey reports whose
>> baseline data never get digitally annotated, let alone cross-referenced
>> against museum collections or taxonomy databases. Ironically, such reports
>> probably have more weight in environmental decision-making. I think that
>> having information from different sources in one digital system where
>> taxonomic inconsistencies become glaringly visible is a step in the right
>> direction. Thank you for your efforts in trying to clean up the resulting
>> taxonomic issues.
>>
>> Best wishes
>> Alex

>> Quality information is critical, but it's difficult to formulate a
>> standard
>> when different taxa vary greatly in their key features. For many animals,
>> dissection showing reproductive features is critical, and often
>> challenging
>> *(e.g*., microscopic). Others have key differences in a specific part.
>> Barcodes have great potential for facilitating identification, but only if
>> the validity of the barcode is tested for the group in question and
>> specimens are carefully identified.
>> As with any online compilation, content must be accompanied by appropriate
>> curation. There needs to be a quick way to communicate information (such
>> as corrected identification) to a responsible party. In the case of
>> barcoding, where often large numbers of specimens are quickly processed,
>> it's particularly important to have a clearly designated identifier for a
>> particular specimen. It's frustrating to notice an error in a barcoding
>> project, search through several pages to finally find some contact
>> information, and then be told that the submitted identifier (the one used
>> in GenBank) was not the proper identifier to enable them to tell which
>> specimen had the problem. At least they could have given some sort of clue
>> as to what the correct identifier would have been ("the one where you've
>> got a photo of something from a different order" wouldn't do, either).

>> > - "Physical specimen" is not a term regulated by the ICZN. In fact, the
>> > word "physical" appears exactly zero times in the entire text of the
>> > Code; and given the definition of "specimen" there, an "un-physical
>> > specimen" (Stephen used the word "ghost" recently) seems to be an
>> > impossibility. Specimens are always physical, or they would be no
>> > specimens.
>> >
>> > - What comes closest in the ICZN to what some seem to call "physical
>> > specimen" is "extant specimen" ("sp?cimens qui existent toujours" in the
>> > French text).
>> >
>> > - For names published after 1999, Art.16.4.2 gives explicit additional
>> > requirements for availability in the special case where the holotype or
>> > syntypes are extant specimens. As this is clearly treated as a special
>> > case, it is obvious that having extant specimens as types cannot be
>> > understood as a general requirement for all species-group names
>> > published after 1999.
>> >
>> > - Again, it is a complete misreading to pretend that:
>> > "73.1.4. Designation of an illustration of a single specimen as a
>> > holotype is to be treated as designation of the specimen illustrated;
>> > the fact that the specimen no longer exists or cannot be traced does not
>> > of itself invalidate the designation."
>> > ...introduces an exception to a general "rule" that would say that a
>> > holotype must be an extant specimen. Should such a "rule" exist, this
>> > article would actually not allow any exception to it: the designation of
>> > the illustrated specimen would be allowed only if the specimen is
>> > extant; the designation of the illustration would have to be treated as
>> > the designation of the specimen; thus, should the specimen not be
>> > extant, the designation of the illustration would not be allowed.
>> >
>> > The truth is that there is NO such rule in the Code.
