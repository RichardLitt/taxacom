Hi Quentin,

Put DOIs on the things that you want to cite or otherwise refer to. Should specimen have DOIs? Yes, absolutely (some already do). That way we can refer to the specimen when we put sequences in GenBank, images in Morphbank, and list it in material examined.

DOIs can also be digital things (e.g., an article which only exists online). We could also have DOIs for sets of things (e.g., a particular set of records that form a data set).

Yes, there will be a lot of of DOIs. But, hey, there are a gazillion URLs out there and we seem OK with that.

Regards

Rod

>> I have two standard responses to this question:
>>
>> 1. Who cares about versions? No, really - we keep worrying about this, but does anybody actually take versions into account? For example, GenBank has versioned DNA sequences and I have never seen anyone cite a sequence accession number AND version. So, to a first approximation, I don?t think this is the issue people make it out to be. Anyone every seen a versioned link to a Wikipedia page?
>>
>> 2.OK, so you really, really, care about versions. Then I think one answer is to provide a DOI for the data e.g., 10.1234/data (which you can think of as either all the versions, or the latest version), and a DOI for each version (e.g., 10.1234/data.v1, 10.1234/data.v2). If, like most folks, you couldn?t care less (?just give me the latest version please?) then you?d use the DOI for the data (10.1234/data) that resolves to the latest version. If you care about the version (e.g., reproducibility is your thing) then use the DOI for the particular version (e.g., 10.1234/data.v1).
>>
>> There are examples of versioned DOIs in the wild. For example, http://dx.doi.org/10.12688/f1000research.2-92.v1 is a versioned DOI. CrossRef supports versions through Crossmark http://www.crossref.org/crossmark/i to handle things like errata, retractions, etc.

>>> Agreed!  I forgot to mention that the archived snapshot documents in our
>>> planned system would be assigned persistent identifiers (most likely DOIs).
>>>
>>> However, this raises another issue that I have not seen adequately addressed
>>> in any of these discussions about identifiers for datasets (including DOIs):
>>>
>>> Is there an expectation that the object represented by an identifier remains
>>> static?  In the case of traditional publications, this seems to be the case.
>>> When I dereference a DOI, I get a digital document (or a landing page for a
>>> digital document).  In my mind, that DOI identifies the conceptual object
>>> (i.e., the published work as an abstract entity, not any particular digital
>>> manifestation/instantiation of the published work, such as a particular PDF
>>> file on a particular hard drive somewhere).  But in the case of
>>> "traditional" publications (including electronic publications, and as
>>> opposed to datasets), the content of the object is expected to remain static
>>> over time.  A hundred years from now, when I (more likely my grandchildren)
>>> dereference a DOI, they will get the same information content (at least at a
>>> human-perception level, if not a bit-identical data file) that I get today.
>>>
>>> Now, I know lots of people (particularly Rod) like to say we should assign
>>> DOIs to "datasets".  That's fine, and totally within scope of what DOIs were
>>> intended for.  But is it implicit that a DOI assigned to a dataset is
>>> actually assigned to a *snapshot* of that dataset at a particular moment in
>>> time?  Or is the DOI representing the conceptual notion of the dataset,
>>> which changes in content over time?
>>>
>>> So, I could assign a single DOI to the Bishop Museum fish collection
>>> dataset, representing the "conceptual" notion of the Bishop Museum fish
>>> collection dataset.  Tomorrow the content is likely to be different from
>>> what it is now. To me, this seems to border on useless. One of the critical
>>> issues of citing databases that comes up again and again is to include the
>>> date on which the dataset was accessed (see my previous post).  Is that date
>>> part of the permanent DOI metadata?  If so, there may be hundreds of DOIs
>>> issued for the Bishop Museum fish collection dataset, each one representing
>>> a particular moment in time for which someone wishes to be able to cite the
>>> dataset content.
>>>
>>> Glancing over through the DOI specification, it seems to me that there is an
>>> implicit assumption that the document identified by a DOI is static in
>>> content.  But I haven't read it thoroughly, and am by no means an expert.
>>>
>>> So, my question to Rod (and anyone else) is:  if we assign an identifier
>>> such as a DOI to a dataset, is there an expectation that the dataset
>>> indicated by the identifier is static?  Or, might it be dynamic?  In the
>>> parlance of LSID-speak, what is implicitly the "data", vs. the "metadata"?
>>>
>>> Aloha,
>>> Rich

>>>>> a result-set back, then upon deciding that this result-set is the one

>>>>> the person constructing the query, and the database owner], full data

>>>>> future access, and would be the digital object cited in the work for

>>>>> We never followed through with the development of that concept (budget

>>>>> directly into a publication venue such as the Biodiversity Data Journal.
>>>>>
>>>>> Speaking of that journal, we are planning to publish a regional
>>>>> checklist (fishes of the Northwestern Hawaiian Islands) in BDJ that
>>>>> changes the way such regional checklists are created.  Basically, we
>>>>> build an evidence-based checklist of occurrence records for
>>>>> within-scope taxa at within-scope region, and store this in a
>>>>> database.  The checklist is annotated and curated by the authors, who
>>>>> vet all the data, flag dubious records, confirm taxonomic
>>>>> identifications, etc.  The checklist is then published in a highly
>>>>> structured form (ala BDJ), with a link back to the database.  The link
>>>>> would then go to a page that displays everything as it appeared in the
>>>>> published version, as well as all data that were altered or added
>>>>> since the moment of publication.  The "vetted" (published) records
>>>>> would be formatted clearly to distinguish from all the un-vetted,
>>>>> "raw" data that became available following the publication.  That way
>>>>> people who come to that website could see the full content of what was
>>>>> published, *AND* all of the new information that has become available
>>>>> since the time it was published.  Eventually, when there is enough new
>>>>> information, it would be vetted again and a new-snapshot generated and
>>>>> published (in the form of a "revised" checklist, or new-records paper,
>>>>> or whatever).  The idea is to be able to clearly show the full dataset
>>>>> as it was snapshot-published, and also give acces to up-to-the-moment
>>>>> additional data; thus avoiding the current problem with regional
